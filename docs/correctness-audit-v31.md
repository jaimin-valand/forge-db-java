# ForgeDB Correctness Audit - v0.31

## Scope

This audit targets observable database semantics rather than architecture alone. It covers numeric predicates, ordering, uniqueness, statement atomicity, transaction rollback, schema metadata, persistence and regression-gate integration.

## Findings and repairs

### 1. Numeric predicate semantics

Integer comparisons were previously vulnerable to lexical ordering in the database-level mutation/filter path. For example, textual comparison could treat `10` as less than `2`. ForgeDB now parses integer operands when possible and falls back to lexical comparison for text values.

### 2. Multi-row UPDATE atomicity

A constraint failure during a multi-row UPDATE could occur after earlier matching rows had already been modified. The UPDATE path now builds candidate versions, validates the complete statement, and only then mutates the table.

### 3. UNIQUE / PRIMARY KEY collision detection

Constraint validation now checks the transaction-visible state and all candidate rows generated by the same UPDATE statement. This prevents two rows from being assigned the same unique value within one statement.

### 4. Transactional schema metadata

Transaction snapshots now include `schemaVersion` and `migrationHistory`. Rollback therefore restores both physical table state and catalog metadata.

## Regression coverage

The dedicated `CorrectnessAuditTest` verifies:

- numeric `WHERE` comparison;
- numeric `ORDER BY`;
- multi-row unique collision rejection;
- statement atomicity after a rejected UPDATE;
- schema-version rollback;
- migration-history rollback;
- persistence after rollback.

The dependency-free release gate completed **11/11 scenarios successfully**.
